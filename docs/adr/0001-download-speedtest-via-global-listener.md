# 0001 - 下载测速采用 GLOBAL 专用通道与限时下载

mihomo 没有按节点测带宽的 API(延迟端点只返回 TTFB),下载测速必须让真实流量经被测节点。决定:配置生成时注入一个仅绑定 127.0.0.1 的专用 mixed listener(`proxy: GLOBAL`);测速命令按「`PUT /proxies/GLOBAL` 切到被测节点 → 从专用端口发起限时下载 → 恢复 GLOBAL」执行,不触碰任何用户分组的选择。这样正确性不依赖规则路由,嵌套子组与 provider 节点也能测;代价是多占一个本地端口,且 global 模式用户在测速窗口内流量会被波及。listener 绑 GLOBAL 需实测验证;若不可行,回退为「切换被测分组 + /connections 链路校验」。

## Considered Options

- Cloudflare speed 端点作为下载源:大小可控,但易被 403/风控拦截,节点间结果不可比,弃用。
- 完整下载固定文件:结果更稳,但每节点消耗整份文件(~200MB),整组测速流量不可接受。
- 切换被测分组 + mixed port 下载:零配置管线改动,但嵌套子组在主组未指向它时会静默测到别的节点的速度,只能靠 /connections 校验降级为报错,该类分组实际不可用,且需额外的测速竞争中止逻辑。

## 修订(2026-10-01):崩溃残留与 GLOBAL 恢复日志

上文的「恢复 GLOBAL」依赖进程内存活的 Drop 守卫;进程被 kill -9 / 断电时守卫不执行,而 mihomo 会把 GLOBAL 选择持久化到 cache.db,残留跨会话存活——global 模式下用户流量会真的走到被测节点,直到手动切换或下次测速覆盖。补充机制:切换 GLOBAL 前先把「原选择 → 被测节点」写入应用数据目录的恢复日志(WAL,写入失败则放弃本次测速),恢复成功后删除;内核启动时检查日志——GLOBAL 仍停在被测节点则恢复原选择,已被覆盖(用户手动切换过)则仅清理不恢复,恢复失败(原节点已随订阅更新消失)则记日志放弃,不猜测用户意图;GLOBAL 读取失败(内核未就绪)保留日志待下次启动重试。

### Considered Options(补充)

- 启动时无条件重置 GLOBAL:实现最简单,但会覆盖用户在 global 模式下的合法选择持久化,弃用。
- 不处理、接受残留:零成本,但 global 模式用户可能长时间流量走错节点,弃用。
- 恢复失败后保留日志反复重试:节点永久消失时每次启动都失败一次,无收敛收益,弃用(保留日志仅限「GLOBAL 读取失败」这类瞬时故障)。
